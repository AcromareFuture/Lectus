# 数据迁移与兼容说明

这是服务化后的新空库基线，不是对旧数据库直接升级的脚本。新库迁移版本从各服务自己的 V1 开始，切勿将旧 MySQL/H2 JDBC 地址直接指向这些迁移，也不要设置 baseline-on-migrate 掩盖版本冲突。

1. 保留旧单体库、外部会员库、旧应用配置和离线备份；本次代码改动没有连接或修改远程数据库，也没有读取桌面会员数据库和私有凭据。
2. 在隔离环境创建四个 PostgreSQL 库和账号，运行各服务初始化；验证 Flyway 成功。会员的 V1 来自已有本地兼容基线，部分完整会员项目实体需要的表尚不在此基线中，不能当作外部完整生产库的最终迁移。
3. 旧 `accounts/auth_sessions` 导入 identity，保留 ID、哈希、过期时间；旧可售商品、SKU、购物车、地址、订单及明细导入 trade，先商品后 SKU、订单后明细。trade 不再引用 identity 的账号外键；account_locks 在用户写操作时按需创建。确认无孤儿 account_id。
4. `catalog_*` 导入 catalog，保持来源 IDs、审核状态与 3D 配色绑定；对象存储文件不移动，设置 ASSETS_ORIGIN。导入工具路径为 backend/tools/catalog，使用 psycopg 和环境变量 CATALOG_DATABASE_URL，不再读取旧 remote.json。源包需显式传 --source；默认 dry-run，--apply 会上传文件并提交事务。
5. 会员生产数据需要逐表字段映射、时间与枚举转换、缺表补齐、索引核对和迁移校验，不能复制旧 H2 文件到新 profile。`BIGINT GENERATED BY DEFAULT AS IDENTITY` 允许保留旧主键；导入显式 ID 后必须通过 setval 修正每个 identity 序列，避免下一次 INSERT 冲突。
6. 对账行数、业务金额、库存、账号唯一键、时间、会话有效性和幂等结果；先只读比对，再按维护窗口停止旧写入、迁移尾差并切换流量。此迁移流程尚未自动化或执行。

PostgreSQL 方言改动包括：移除 MySQL 驱动与分页方言，使用标准 identity/timestamp/smallint，INSERT IGNORE 改 ON CONFLICT，导入工具使用事务级 advisory lock，JSON map 的驼峰别名增加引号。旧 ON UPDATE CURRENT_TIMESTAMP 改为应用字段更新；若生产表依赖数据库自动更新时间，必须在后续迁移中增加明确的更新规则或触发器并核验。

回滚需要旧应用及其旧库快照；新旧应用不能交替写同一个数据库。只有源码/配置有本地备份，不代表业务数据已有完整回滚方案。旧 backend/data 和 target 被保留，新配置不自动使用。

目前只完成 H2 PostgreSQL 兼容模式的自动测试和多进程 HTTP 联调。真实 PostgreSQL 17、容器镜像、导入脚本真实写库和完整会员生产表兼容性仍需在部署环境验证。
