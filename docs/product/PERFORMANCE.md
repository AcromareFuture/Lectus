# 性能约束与验收

更新：2026-10-24。适用于后续功能扩展和技术接入。本文件定义目标与验证方法，不代表项目已通过容量验收。

## 当前代码检查结果

1. `FeedService.feed()` 使用 ID 游标和每页 12 条的边界，但逐条调用 `decorate()`，分别查询作者、关注、点赞数、收藏数、评论数、本人点赞/收藏及媒体。普通作者、已登录访问者的一页最多约 `1 + 12 × 8 = 97` 次 SQL。应先改为按本页 ID 集合分别批量获取作者、媒体、聚合计数及本人状态，再组装响应；不能用一个多表连接把点赞、评论、媒体展开后重复计数。已有用户状态不可进入共享公共缓存。评论作者查询也需要同类处理。
2. 当前生产构建入口 `index-DKMgL6wx.js` 为 584,429 字节，CSS 为 123,212 字节，均为未压缩制品大小。社区、设置、订单等页面仍被入口静态导入，适合按路由拆分；必须检查拆分后的网络瀑布与共享依赖，避免只把文件变多。`model-viewer` 为 1,040,254 字节，已经动态导入，保持仅在打开 3D 时加载；保留首页效果。
3. 商品搜索通过 `POSITION` + 拼接字段匹配，普通 B-tree 不能直接优化此类条件；目录接口还包含总数查询、相关子查询和 OFFSET 分页。应先用代表性数据检查 `EXPLAIN (ANALYZE, BUFFERS)`，再决定索引、计数策略和游标接口。不能仅安装 `pg_trgm` 就认为已有查询会自动使用索引。
4. 上轮生产主机快照中，可用内存约 283 MiB，未配置 swap。该数字是瞬时观察，并非持续余量。新增常驻服务前需观测峰值 RSS、PG、文件缓存、GC 与媒体 IO；Swap 不能替代容量。
5. 仓库 Nginx 配置已开启 gzip，静态资源统一缓存一小时。后续可为带内容哈希的 JS/CSS 配置长期 immutable 缓存，入口 HTML 继续更新校验；发布清理需保留旧分块，避免旧标签页动态导入失败。实际生效情况以部署检查为准。

## 初始验收目标

下面是待验证的目标；不得将其表述为已经达到的性能。

| 范围 | 初始目标 | 口径 |
| --- | --- | --- |
| 用户页面 | LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1 | 手机端真实用户 p75；实验室固定设备/网络单独记录，不能混用 |
| 普通查询接口 | p95 ≤ 300 毫秒、p99 ≤ 800 毫秒 | 在声明的目标负载下，从网关计时；不含媒体下载和外部服务耗时 |
| 交易提交 | p95 ≤ 500 毫秒 | 本地订单持久化阶段，不含支付渠道、短信等外部处理；库存和金额正确性必须先通过 |
| 可靠性 | 非预期失败率 < 0.1% | 包含服务端错误、超时及非预期业务失败；预期校验拒绝和限流单列 |
| 社区列表 SQL | 返回 1 条或 12 条时，查询次数保持固定上限 | 批量改造后建议已登录列表 ≤ 8 次；并检查数据库执行耗时和扫描量 |
| 前端首屏 | 按入口 gzip 传输、请求瀑布及长任务建立基线 | 首页不请求社区发布、订单、设置实现和 3D 引擎；有理由的预取单独记录 |
| 资源余量 | 目标峰值负载下仍保有约 25% 内存余量 | 同时检查连接池等待、CPU、磁盘 IO、GC 暂停，不能只看平均 CPU |

先测出稳定容量，再确定业务承诺。并发在线人数、并发请求数和 RPS 分别报告，不互相替代。对已有稳定基线，新增功能导致相同环境下 p95 或首屏传输量回退超过 10% 时，须说明原因并修复或明确接受。

## 实施顺序

1. 先批量化社区读取，补查询次数与结果正确性回归用例，覆盖匿名/登录、空列表、关注/收藏、计数为零和多媒体内容。无需为此增加 Redis 或独立微服务。
2. 再做路由按需加载，检查刷新、慢网、加载失败重试和旧版本分块兼容；保留 Hero、卡片及按需 3D。
3. 在隔离环境建立 PG 代表性数据、热点与长尾分布；分别测冷缓存、热缓存、混合读写、登录与匿名流量。记录数据量、硬件、软件版本、连接池与请求分布，使结果可复现。
4. 以恒定到达率逐级增加请求，记录 p50/p95/p99、实际吞吐、失败/限流率、未能发出的请求、SQL 次数、连接池等待、CPU/RSS、GC 和 IO。先校准负载机，避免负载生成不足造成虚假的低延迟。不对现有生产商城执行压力测试。
5. 交易验证同时检查库存不超卖、幂等不重复扣减、支付回调重复/乱序可恢复。缓存与异步化不能绕过 PG 的业务约束。
6. 按实测结果决定容量、索引、缓存或服务拆分。日志/指标设置采样与保留周期，禁止让全量正文日志和无限标签拖慢请求。

## 技术接入边界

- Java 与 PostgreSQL 继续承担核心事务；只读列表、计数及媒体读取分别优化。连接池总上限按所有服务和副本累加，给迁移与运维连接留余量；不能盲目扩大连接池。
- 缓存仅针对允许短暂陈旧的数据，定义键、TTL、失效和击穿保护。价格、库存、权限和支付状态按业务要求校验。
- OSS/CDN 与异步转码用于分担媒体网络/CPU/IO，需评估费用、回源、失败重试和审核状态；本轮未接入。
- 外部服务设置超时预算、并发上限、重试上限与幂等。任务队列有容量、积压监控和死信处理；过载时限流、背压，不能无界堆积。
- 新微服务需要明确的独立伸缩或隔离收益，并承担 RPC、连接池和常驻内存成本。Go、搜索引擎、RabbitMQ、Kubernetes 均由瓶颈和需求决定，不能作为性能保证。

本次仅完成静态代码检查和约束整理，未执行新的压力测试、性能代码修改或生产发布。自动化功能检查通过不能替代性能验收。
